# M1 dependency inventory and third-party review — #54

**Status:** inventory automation, **not** completed legal/security approval. This is a developer engineering aid for the proposed, unpublished `v0.2.0-alpha.1`. The development package remains `0.1.0`.

## Evidence written by clean-install CI

[CI](https://github.com/interzettel/kushluk/actions/workflows/ci.yml) builds the wheel and source distribution twice and installs **each** in its own empty virtual environment outside the source checkout. During both installs, `tools/release_check.py` now:

1. Uses `python -m pip check` to check declared Python dependency compatibility.
2. Executes `tools/release_inventory.py` using the **isolated installed venv's Python**, not the repository Python.
3. Writes `wheel/installed-environment.json` and `sdist/installed-environment.json` alongside the synthetic fixture and `release-evidence.json`.
4. Records the inventory's SHA-256 digest and actual installed package count in each `installs` entry in release evidence.

The inventory captures normalized installed Python distribution **name**, resolved **version**, declared `License-Expression` when available, and whether a license classifier/legacy field exists. It excludes private source paths, metadata locations, installation URLs, account credentials, raw license texts and complete distribution metadata. Pip/setuptools/wheel, when installed, are explicitly labeled as tooling but are still included in the environment snapshot.

This is an **installed-environment inventory**, not a formally generated SPDX/CycloneDX SBOM, vendored-code audit, trademark clearance, dependency lockfile, reproducible end-to-end supply-chain attestation, or proof of production vulnerability absence. A package claiming MIT or BSD metadata has **not** been independently license-reviewed merely because the field exists.

## Additional automated evidence (non-release)

The [Python vulnerability audit workflow](../.github/workflows/dependency-audit.yml) runs on a reviewed dependency/workflow change, weekly, or by manual dispatch. In an isolated Python 3.12 environment it installs the project's declared runtime extras (including PDF and Google adapters), freezes exact resolved third-party versions (excluding the editable local development package), checks dependency consistency, and invokes the maintained [PyPA pip-audit](https://github.com/pypa/pip-audit) against public PyPI vulnerability advisories. A scan with known advisories or an unavailable vulnerability service fails the workflow; neither is reported as clean. The runner retains the public-package version list and JSON findings for 14 days. It never executes autofixes or uploads local reader data. This workflow uses current network advisories, unlike the offline M1 inventory.

The existing native macOS CI job also records optional `pkg-config --modversion` observations for Pango, Fontconfig, HarfBuzz and Cairo and `fc-match` **family names only** for generic sans, serif and monospace. The create-only JSON is generated by `python -m tools.native_inventory --output output/native-evidence.json`. Missing system commands are recorded as unknown values, not interpreted as safe or absent. No actual font files or system paths are collected. Neither library versions nor family identity establishes font embedding rights, dependency licence compatibility, macOS reproducibility or real printer behavior.

**Interpretation:** a passing Python advisory scan only means the dependencies resolved by that workflow had no published findings from its configured vulnerability service at that time. It is not an SBOM, review of assets/native licences, assurance of zero vulnerabilities, proof of source permissions, or approval to publish.

## 17 October 2026 advisory finding and remediation candidate

The **first live scan** on [PR #124, run 39044303399](https://github.com/interzettel/kushluk/actions/runs/39044303399) **failed for a real finding**, not a scanner error. The isolated PDF-extra install resolved **WeasyPrint 69.0**, with two published identifiers (`PYSEC-2026-3940` / `CVE-2026-55073`; `PYSEC-2026-4311` / `CVE-2026-106443`). The advisory database listed **70.0** as the fixed version for both; upstream explicitly describes 70.0 as a security release, including EPS blocking and URL-fetcher propagation fixes. See [upstream changelog](https://github.com/Kozea/WeasyPrint/blob/main/docs/changelog.rst).

The code's previous dependency bound `weasyprint>=62,<70` prevented pip from selecting the security fix. PR #124 changes this to **`weasyprint>=70,<71`**. This is a remediation **candidate** until the updated advisory workflow and full four-page Linux/macOS PDF regression matrix have passed. We have not reproduced an exploit in Kushluk, and dependency advisories are not evidence that any user has been compromised. Runtime still requires native font/lib inspection and restricted untrusted assets.

## Installed Python component manifest (software-only evidence)

The weekly/on-demand [Python advisory workflow](../.github/workflows/dependency-audit.yml)
also now saves a deterministic **CycloneDX 1.5 JSON installed-environment inventory**
(`installed-python-components.cdx.json`) from the same isolated Python 3.12 environment
as the live advisory scan. Run manually with `python -m tools.python_sbom --output
output/security/installed-python-components.cdx.json` inside the desired environment.
It contains public normalized Python package names, versions, PURLs and only explicitly
declared SPDX `License-Expression` text when present. It does **not** contain paths,
private reader content, full dependency graph, exact wheel hashes, native libraries,
fonts or a resolved release lockfile. Its bytes are deterministic for the same installed
package metadata; the create-only private output does not silently overwrite evidence.

**Important:** an installed-dependency component inventory is not a signed, validated
release SBOM. The scan may contain packages from optional extras and build tooling;
the actual shipping distribution can resolve different dependency versions. SPDX metadata
is not legal signoff. Native/font redistribution rights, transitive obligations,
provenance and binary reproducibility still need the independent release review.

## Per-install licence-review worksheet (review pending)

Each clean **wheel** and **sdist** installation now creates a hashed
`license-review-worksheet.json` beside its `installed-environment.json`.
This fixed-schema worksheet assigns every installed Python distribution an
explicit **pending** licence-review row and classifies its metadata as
declared SPDX expression, classifier-only, legacy field, or missing. It also
includes four native libraries (**Pango, Fontconfig, HarfBuzz, Cairo**) and
three font-family match queries (**sans-serif, serif, monospace**) as pending
independent reviews. The source snapshot hash is included; the result is
not an approval.

To combine a locally saved native inventory with a clean-install inventory:

```bash
python -m tools.license_review_matrix \
  --python /PRIVATE/installed-environment.json \
  --native /PRIVATE/native-evidence.json \
  --output /PRIVATE/reviews/license-worksheet.json
```

Without `--native`, those native/font rows are still present but explicitly
unobserved. A CI-installed runtime is **not** the same as an exact pinned release
dependency graph, and numeric native versions do not identify fonts bundled or
embedded into a PDF. Reviewers must separately establish and record actual
licence texts and fulfil attribution, embedding and redistribution obligations;
the worksheet neither copies licence text nor grants rights. Machine-generated
rows always have `approved_for_release=false`, and a human must sign off
separately outside the generation tool. No fonts are uploaded or bundled.

## What remains before publishing anything

- Inspect each transitive Python distribution's actual license and retained notices; verify bundled code/assets/fonts and any incompatible terms.
- Audit native WeasyPrint/Pango/Fontconfig/Harfbuzz/cairo and OS/brew dependencies on both macOS architectures and the selected Linux baseline.
- Run a separately approved, timestamped vulnerability check with current advisories. Offline metadata alone does not detect CVEs.
- Pin/review reproducible release dependency versions or a platform-specific constraints policy. Wheel/sdist byte reproducibility within a runner does **not** guarantee identical dependencies next month.
- Decide whether publishing warrants a standard SPDX/CycloneDX SBOM and automated provenance attestations, then version those outputs rather than mislabeling this provisional JSON.
- Obtain a human release decision before any `v0.2.0-alpha.1` version bump/tag/signature or GitHub Release.

The root [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) distinguishes dependencies installed from PyPI from code/assets copied into the project. [SECURITY.md](../SECURITY.md) explains how to report private findings. Candidate artifacts live in CI for 14 days and must never include reader archives, email headers or API tokens.
